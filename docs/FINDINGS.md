# Findings: reShapr on apple/container

Tested 2026-11-11 on macOS 27.2 (build 26B123), Apple silicon, `container` 1.7.1 (extracted from the release `.pkg` into a user directory, no sudo), reShapr 1.1.0 images from `registry.reshapr.io`.

## Findings

- **F1 No compose-equivalents.** Script uses `container exec ... pg_isready` and a curl loop instead of `depends_on`/`healthcheck`. No `--restart`: a crashed container stays stopped.
- **F2 Name resolution needs sudo even container to container.** Containers register as `<name>.test` (seen in `container system logs`), but a container's resolver (192.168.65.1) forwards to macOS, which only knows `test` after `sudo container system dns create test`. Without it: `NXDOMAIN`/`UnknownHostException`. Docs describe it as two steps, but that the in-container lookup depends on step 2 is easy to miss. Confirmed: after `sudo container system dns create test`, `dnsa.test` resolves from another container. `host.container.internal` also needs sudo, and its packet-filter rule is removed on restart (`docs/host-integration.md`).
- **F3 Shared alias rejected, DNS answers one A record.** Plain containers cannot form a DNS_PING cluster (needs several A records for one name). Use `container cluster` (T7, where the Kubernetes headless Service provides them).
- **F4 `container cluster` kubeconfig uses `rs.test`**, same sudo dependency. Workaround: `--server https://<node-ip>:6443 --insecure-skip-tls-verify`. `cluster create` also rewrites `~/.kube/config` and sets current-context (`cluster delete` removes its entries but not the current-context).
- **F5 `--shared-image-store` works**: pods ran locally pulled reShapr images without a registry.
- **F6 Host-to-container by IP works** (192.168.65.x via bridge101); first connection once failed with "no route to host" and succeeded on retry.
- **F7 Docker Desktop port clash.** A running Docker reShapr stack on 5555/7777 made the readiness probe false-positive. `up.sh` ports are configurable for that reason.
- **F8 (reShapr, independent of container)** `reshapr-k8s` stack requires a JCEKS keystore (`reshapr-cluster.jceks`, `reshapr.infinispan.encrypt.*`); without it the gateway returns HTTP 500 on first MCP request (`ISPN000541 ... FileNotFoundException: reshapr-cluster.jceks`). `install/docker-compose-cluster.yml` at reshapr 3dd7a4c sets no keystore, and running it unmodified on Docker (Compose v5.6.1, `:nightly` images) gives the same result: both gateways report ready, then the first MCP `initialize` returns HTTP 500 with the same `ISPN000541 ... FileNotFoundException`. Confirmed upstream bug, not an apple/container limitation. Filed as reshaprio/reshapr#621 and fixed on `main` (keystore-init container in `docker-compose-cluster.yml`); not re-tested here.
- **F9 (reShapr)** Gateways that start before the control plane is ready log `Failed to fetch expositions during startup` and do not retry discovery until restarted (rollout restart fixed it). Compose `depends_on: service_healthy` hides this; Kubernetes needs an init wait or retry.
- **F10 `postgres:17-alpine` pull** unpacked several platforms (`linux/s390x` seen in output), about 2 min first time; reShapr images about 1 min each.
- **F11 (reShapr, K8s) per-pod keystore init container does not work** (2026-11-14, reShapr 1.1.0 images, `container cluster`). Replacing the `reshapr-cluster-keystore` Secret with an init container running `keytool -genseckey` into an `emptyDir` (the approach of upstream's compose fix for #621) gives each gateway pod a different AES key (different keystore hashes). Gateway 2 then logs `GMS: JOIN(...) sent to <gateway 1> timed out (after 2000 ms)` repeatedly and gateway 1 stays coordinator of a 1-member cluster. So on Kubernetes the keystore must be shared (the Secret in this repo, or a one-shot Job that creates the Secret). Caveat: an MCP session created on gateway 1 was still accepted by gateway 2 in that broken state, so the T7 "session shared" check does not prove clustering. **Re-test of T7 with the shared Secret (2026-11-14, same images):** both gateways share one keystore; gateway 1 logs `no members discovered after 2.00s: creating cluster as coordinator`, gateway 2 starts its channel afterwards and logs no `JOIN ... timed out` (0 occurrences on both), i.e. it joined. Sessions created on either gateway are accepted by the other. The cache starts lazily, so the cluster only forms after the first MCP request on each gateway. Remaining gap: no explicit view-size log or metric was available to confirm a 2-member view. Also seen again: gateways started before the control plane was ready (or before the import) missed the exposition until `rollout restart deploy/gateway` (F9).

## Upstream candidates

- reShapr: done: `--engine apple` (#619, #620) and the compose-cluster keystore (F8, #621). discovery retry (F9): filed as [reshaprio/reshapr#628](https://github.com/reshaprio/reshapr/issues/628). To file: configurable host alias instead of `host.docker.internal`.
- apple/container: egress allow-list (T8): done, commented on [discussion #719](https://github.com/apple/container/discussions/719#discussioncomment-19611430) (related [#1320](https://github.com/apple/container/issues/1320)); multi-A / shared alias (F3), host-side DNS not required for container-to-container lookup (F2), kubeconfig by IP (F4), healthcheck/restart.

## Not verified

macOS 15 behaviour, `host.container.internal` surviving a reboot.
